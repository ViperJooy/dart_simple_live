# 斗鱼断流恢复验证

## 已复现的问题

2026-10-19 在 macOS 实际运行应用、打开斗鱼直播间后，观察到多轮约五分钟断流后的两种失败：

- 播放时间反复回到 0～几秒，一分钟内无法连续播放十五秒。
- 播放时间连续四十五秒不推进，持续缓冲，自动恢复失败。

第一次自动重连成功不能证明长时间观看正常；`playing=true` 或播放时间偶尔变化也不能作为恢复成功的充分条件。

故障现场仅替换 `detail.data` 为重新取得的签名，保留原清晰度与 CDN 列表，再请求播放地址，连续播放恢复正常。旧实现虽然重新调用播放接口，却一直复用进入房间时的 `tt/sign`。因此需要在核心站点实现中每次重新签名，而不是依赖用户手动刷新整个房间。

此外，恢复链路存在三个放大故障的问题：

- 冷却或已有刷新时返回 `false`，媒体回调随即 `jump` 旧地址，可能打断正在加载的新流。
- 冷却结束后取流接口暂时失败，且没有新 EOF／缓冲事件时，恢复任务会丢失。
- 新播放列表未指定起播 index，实际线路与界面选中的线路可能不一致。

## 离线回归

在 `simple_live_core` 目录运行：

```sh
dart run test:test test/douyu_play_signature_refresh_test.dart --reporter expanded
```

测试不访问网络：Dio 返回人工房间数据和人工签名脚本，但执行真实 QuickJS 签名入口。同一个 detail、清晰度和 CDN 列表跨秒连续取流三次，检查每次 `tt` 属于本次调用时间范围，且签名与 `tt` 对应。旧实现已确认失败，修复后通过。

在 `simple_live_app` 目录运行：

```sh
flutter test --no-pub --reporter expanded
```

`test/live_room_stream_recovery_test.dart` 保留真实控制器取流、冷却及播放列表调用链，仅替换网络站点和播放器平台层。覆盖：

- 选中线路作为播放列表的起播 index。
- 在途刷新期间 EOF／error 不重放旧地址。
- 冷却内多个 EOF 合并为一次延后刷新。
- 接口暂时失败后，无须新媒体事件也会继续重试。
- 关闭时取消排队任务，并忽略迟到的响应和媒体回调续体。
- 手动切线取消过期的排队刷新。
- 开启后台自动暂停时不擅自重启播放，回前台后再恢复。

这些离线测试不能替代真实 CDN、libmpv 和视频画面的验证。

## 实机复测要求

1. 实际启动 macOS 应用并打开正在直播的斗鱼房间，确认视频画面，不只检查启动成功。
2. 记录不含鉴权信息的 `playing/buffering/completed`、播放时间、缓冲时间、应用线路 index 和播放器线路 index。
3. 每五秒采样，至少观察三十分钟，覆盖多轮五分钟到期；默认线路和备用线路均要覆盖。
4. 以下任一情况判失败：
   - 播放时间四十五秒不推进。
   - 连续十二个样本均小于十五秒，表明反复重开而非稳定恢复。
   - 界面线路与播放器实际 index 不一致。
5. 另以本地有效 FLV 停止送数据但保持 HTTP 连接、不发送 EOF，确认缓冲看门狗能自动切回真实 CDN，并单次连续播放超过三十秒。
6. 不输出或提交原始流地址、签名、Cookie、VM Service 地址及完整应用日志。

- 核心签名离线回归通过；应用完整离线套件 34 项通过。

- 签名修复后的自然长测自 14:25 至 15:00，持续 35 分钟，覆盖默认线路与备用线路，记录到 6 次约五分钟自然断流后恢复；测试期间陆续加载了冷却、关闭及后台保护修正。未触发四十五秒停滞或连续一分钟反复重开的失败判据。
- 最终修复的无 EOF 停流注入通过：本地 FLV 停止送数据后进入缓冲，自动换回真实 CDN，并单次连续播放超过三十秒。
